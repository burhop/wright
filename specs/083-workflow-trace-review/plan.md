## Summary

Provide a results-first Trace page for a saved engineering workflow run. Show principal deliverables and previews immediately; reveal the recognizable process graph, individual occurrences, prompts, inputs, decisions, assumptions, and externally produced validation evidence on demand. Preserve partial work and recorded errors for unsuccessful runs. Export a navigable report alone or with all available related data in a portable ZIP.

Build on current run records, artifact representations, workspace services, and viewers. Add durable occurrence/version capture where necessary, then build report projections and portable exports from the same pinned record set. Existing and future workflow or validation producers own engineering checks; this feature consumes their recorded evidence through a producer-neutral contract. No new validators, requirement approvals, or content-validation campaign are included.

## Completed-Process Review Amendment (2026-09-17)

The standalone review describes what happened, in engineering terms, from
supplied inputs to generated outputs. It is not a live workflow or a statement
of planned work. This amendment supersedes the earlier prompt-first activity
drawer and separate activity/handoff index.

- Keep the compact request overview and outputs near the top. Also expose
  supplied text, actual input imagery, and document links in the swimlanes,
  outside the consuming activity. Link to a consumer only when retained records
  establish that relationship.
- In the input overview, count supplied records separately from review-time
  reconstructions. Show the primary prompt, then the supplied file/input list.
  Place any overflow disclosure directly under that list; do not show a detached
  aggregate "Review all" link. Reassembled context has its own disclosure and
  retains access to its source documents.
- Opening an activity starts with its completed engineering purpose, software
  and version evidence, brief input references, recorded passes and timing.
  Execution events, reported operations, decisions/assumptions and engineering
  measurements are available through progressive disclosure. Do not repeat the
  entire user request in every activity.
- Distinguish supplied models from models generated by the workflow and their
  repaired successors. Place produced-file links outside the activity block.
- Integrate activity, file and handoff navigation into the swimlanes themselves,
  including keyboard access and a narrow-screen layout. Remove the duplicate
  activity/handoff index.
- Use compact input blocks matching the activity-block scale. Only the input
  row's disclosure expands its prompt excerpt, image preview and source-document
  groups inside the corresponding blocks. Bound large sets with a remaining-input
  block; keep the recorded consumer connector and full input access in both states.
- Keep workflow passes, internal CAD/tool retries and whole-run AI request
  counts separate. Never infer a revision count from token/request usage or
  present a current installed tool version as the historical version used.
- A producer application/version may be read from bounded, digest-verified
  package metadata. Reading this metadata is not geometry validation. Unknown
  software identity, version, detailed model reasoning or internal retries
  remains explicitly unavailable, not reconstructed.

## Architecture and Design

### Capture and projection

Keep each source execution record authoritative. Add an adapter for the canonical-source run JSON currently produced by `workflow_run_record.py`, and use existing canonical run/step/artifact repositories where applicable. Source adapters retain version and source-record identities rather than normalizing away important status distinctions.

At run start, retain the executed definition/layout and bound input references. At step execution, record actual prompts/context references, occurrence IDs, explicit data transfers, and artifacts at publication before a later iteration can overwrite their paths. Content-addressed or equivalent versioned storage avoids duplicate bytes while preserving separate provenance.

Persist occurrence/evidence records incrementally with idempotent event keys and transactional references to durably published blobs. Capture has no dependency on report generation or a frontend session. Preview rendering is asynchronous. Preserve the original run outcome if capture fails and expose missing evidence locally; never replay a tool to fill a report gap.

Create a small report projection pinned to a capture cursor and evidence revision. Load occurrence lists, documents, raw activity, and large representation bodies only on demand. A new external evidence record can produce a new report revision without rewriting the run or previously exported reports.

### Evidence integration

[The evidence contract](contracts/evidence-integration.md) accepts validation from any authorized producer. The minimum relationship is producer identity plus exact run/occurrence/artifact/requirement subject and supporting references. Request recorded engineering context where the producer has it, rather than adding checks in the report layer.

Use separate facts for execution outcome, externally reported validation, approvals, and artifact availability. Report display must not recompute success, approve a requirement, or treat missing validation as a newly discovered engineering concern.

### Results and drill-down UI

Add a run-specific Trace surface reached from the normal workspace and run history. Initial content is the result set, actual previews, concise purpose, and recorded status. Include a recorded error or blocker when applicable. Assumptions and process detail are expandable.

The graph is a read-only semantic projection of the definition that ran, preserving recognizable blocks, edges, and groups. Prefer saved layout when compatible; otherwise compute a stable readable layout using the existing graph stack. Retain one path and expose an ordered occurrence list for repeat traversal. Use actual producer events to link transfers and attempts.

One contextual detail panel provides progressively disclosed output, input, decision/requirement/validation, prompt, and technical details. It preserves graph selection, scroll, and keyboard focus. An accessible list provides equivalent navigation. Stable subject anchors prepare for later comments without introducing annotation UI now.

### Artifact presentation and export

Reuse result roles, representations, and existing viewer routing. Qualify in-app STEP viewing using the actual available CAD/viewer route; do not advertise a generic 3D component as STEP support. STL is a known inspected capability; 3MF and direct STEP offline viewing need explicit probes. Preserve preview and original-file access when an interactive viewer is unavailable.

The portable exporter bundles the established Three.js STL loader and orbit controls. Family-aware presentation rules select only principal final product geometry, with an 8 MiB per-model bound; retained CFD domains, fixtures, board surrogates, and other analysis meshes remain supporting files. Visual inputs use their verified packaged image representation. WebGL canvas-pixel, desktop/mobile framing, file-origin, and network-blocking checks are required for advertised viewers.

Create a dedicated report exporter rather than altering the verified social capture service. Both export modes use the same pinned report model. Full-data exports include available inputs, outputs, iterations, recorded prompts and activity, and externally supplied evidence. Report-only exports include report content and display assets with deliberate omission states for file bodies.

Use relative navigation, a manifest of identities and byte digests, and bundled assets that work under `file://`. Keep originals intact; label portable document rewrites or model display conversions as derived representations. Generate archives on disk and publish only complete jobs. Existing access rules still apply.

5. **Process and iteration inspection**: Integrate the read-only executed graph, selectable blocks/connections/groups, occurrence lists, version-specific links, and recorded rationale/prompt drill-down. Verify keyboard access, narrow layouts, and preserved authoring.
6. **Portable report and full-data ZIP**: Implement pinned report revisions, archive jobs, relative navigation, original/derived representation distinction, and offline viewer packaging/fallbacks. Test actual file-origin operation after extraction and relocation.
7. **Corpus and integration acceptance**: Inspect all selected cases, record report-link and format coverage, and test stopped runs/loops with labeled additional fixtures. Complete applicable repository checks before any later authorized push/merge.
8. **Campaign-wide publication**: Freeze a 30-case inventory from the reviewed completed selection plus latest retained incomplete attempts. Prepare those exact records read-only, export all or selected cases through the shared renderer, publish one ZIP and extracted report per case with an offline catalog, and verify every package and `file://` page without network access.

Annotations remain a follow-on. None of these steps reruns the engineering campaign or changes its content-validation gate.

## Verification Strategy

| Risk                                         | Required evidence                                                                                                                                                      |
| -------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Run history mistaken for current workflow    | Edit the definition after a run; the report retains the executed definition or explicitly lacks it.                                                                    |
| Same filename overwritten in a loop          | Two retained versions open with their original bytes and occurrence identities.                                                                                        |
| Guessing causal order                        | Parallel and nested execution fixtures link transfers by explicit occurrence IDs, not adjacent timestamps.                                                             |
| Lost data on error/restart                   | Durable captured records survive a forced interruption and remain viewable independently of the browser.                                                               |
| Incorrect attribution of external validation | Different subject hashes/revisions and late/superseding checks retain their exact producer associations without new verdicts.                                          |
| UI overload                                  | Initial screen shows deliverables; graph and technical details remain closed until requested. Review the normal workspace route at desktop/mobile sizes and 200% zoom. |
| Viewer capability overstated                 | Real files, interaction, screenshots, and nonblank canvas pixels for each advertised 3D path; fallback behavior for unsupported formats.                               |
| Export works only on developer machine       | Move extracted ZIP, disable network, use file-origin browser access, follow all generated links, and inspect both export modes.                                        |
| Acceptance overclaimed                       | Frozen 30-case report inventory distinguishes 24 reviewed completions from six retained incomplete attempts; synthetic examples do not count.                           |
| Batch drifts from reviewed report             | Campaign CLI calls the same canonical projection and standalone exporter; no second renderer or per-case page exists.                                                   |
| Incomplete cases look successful              | Six retained failed attempts show exact error codes, stopping reasons, completed activities, and partial files; catalog status remains failed.                           |
| Campaign package corruption                   | Verify all archive members, extracted bytes, and manifest SHA-256 values, then open all 30 reports under blocked networking.                                             |
| Shared branch regressions                    | Run applicable package-boundary, API, browser, and recorder tests after integration.                                                                                  |

Documentation-only planning is checked for links, feature identity, scope consistency, and whitespace. No application tests or live browser verification are claimed by this planning change.
