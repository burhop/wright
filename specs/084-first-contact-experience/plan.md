# Implementation plan: first-contact experience

**Status:** Accepted by goal submission on 23 October 2026; implementation active.
**Branch:** `codex/084-first-contact-experience`, based on planning commit `42e1edd9`.
Feature 084 is active; Feature 083's history and unrelated existing work are retained.

## Journey and existing ownership

Explore a recognizable job → inspect intent → prepare selected capabilities →
start bounded work → inspect engineering results → make one useful change →
reopen or explain a failure. Follow the platform vision/refactoring plan, process
UI design, instruction/interactions plan, demonstration principles, and workspace
UI integration guide linked from root `AGENTS.md`.

| Responsibility | Reuse / boundary |
| --- | --- |
| Starter definition, files and origin | Existing template catalog, workflow bundles and accepted source service; no second package format |
| Setup and capability qualification | Existing registry/readiness/gateway; external provider recipes and usage guides own native requirements |
| Execution, waits and recovery | Canonical source runtime, recorder/storage, reviews, validation/rework and permitted-action contracts |
| Inputs/results/progress | Existing process interaction projection, scoped client, common view and shared UI kit in workspace tabs |
| Editor and exact navigation | Existing WorkspacePanel and reviewed workflow editor; result/block/review identities stay connected |
| Instructions and model choice | Existing versioned assets/settings and adapters; freeze resolved configuration and record observable request provenance |
| Diagnostics | Existing support-diagnostic services, logger/event owners and redaction; local export |
| Delivery metrics | Existing development-metrics collector and CI logs; observational only |

Use existing Python/TypeScript packages, FastAPI application-service boundaries,
SQLite storage, authentication and build tools. Offline exploration must work
without a provider; live capability absence remains explicit. No new vendor
protocol, manager-specific core, telemetry backend or QA dashboard application.

Constitution review: preserve package boundaries, offline fallback, shared native
runtime and distribution obligations, local identity, external tool ownership,
applicable component/journey/system checks, and existing traceability. Historical
constitution examples do not replace current accepted architecture or gate scripts.
Submitting the goal approves this plan's bounded local work without repeated
technical lifecycle approvals; actual engineering reviews keep their authority.

## M1 — Explore and become ready

Package the selected source, lawful sample assets, instructions, validation and
required UI/reference dependencies through existing mechanisms. Imported content
transfers no credentials, approvals, live runs or trusted UI-build authority.
The ordinary workspace offers a useful recorded/sample view without MCP setup,
then routes live use into task-specific readiness and existing setup mechanisms.
Keep reference/setup/ready/verified states evidence-based and revision-specific.

## M2 — Complete and correct the job

Bind the handle to substantive geometry/repair → slicing → package inspection
and independent requirement checks. A minimal parameterization of existing
preparation is preferable to another domain runner; preserve the wheel recipe.
Use actual source/repaired meshes, native profile data, orientations, toolpaths
and support evidence. Do not infer support placement from an attractive preview.

The interaction contract exposes declared inputs, exact outputs/findings,
questions/reviews, observations and permitted actions. Reuse the common working
view; tailored UI is optional and must use the existing versioned kit/client.
Keep the normal workspace editor available and navigate to exact subjects.

Use an already permitted orientation choice for the correction demonstration;
preserve the original requirement to compare both orientations. Selection or
preparation changes invalidate affected packages, checks and decisions. Retain
source/repaired geometry only where existing dependency/identity rules allow it.
Record whether work used bounded rework or an explicit new revision/run; no claim
of arbitrary incremental recomputation. UI-only layout changes do not stale CAD.
Incompatible saved UI bindings fall back to the usable common view.

Record stage timing, estimates and configured limits honestly. Preserve frozen
model/adapter/instruction/tool identities on continuation. Unexpected provider
failure follows existing bounded policy; closing/reopening observes durable state
and cannot replay uncertain operations. Model metadata does not grant reviews.

## Q — One bounded quality-cost improvement

After the baseline, implement the smallest justified consolidation or setup/build
reuse. Preserve distinct OS, installed-artifact, browser and security claims,
package-local isolation, all required unique tests and coverage thresholds.
Update affected Unix/Windows gates, matching CI, regression checks and runbook
together. Reconcile conflicting broad-before-commit guidance with the authoritative
runbook. Changes to gate coverage require the runbook's full validation.

Compare the affected stage under recorded equivalent conditions, separating warm
cache/setup effects. Use enough bounded repetitions to expose material noise;
record unsuccessful attempts too. Prove a representative relevant failure still
fails the gate. No passing receipt is invented or transferred across invalidating
changes. If a candidate does not save measurable cost, record that result and
evaluate one other evidenced candidate; do not expand into an endless QA rewrite.
The saving criterion remains open until demonstrated.
After two unsuccessful candidates, leave AC10/T014 and the goal incomplete and
request a bounded scope/resource decision while completing independent work.
This limit does not authorize further open-ended optimization or an easier metric.

Verify the ordinary workspace entry, preserved authoring controls, common view,
recovery and installed native resources. Independent review checks actual user
behavior and exact evidence. Run applicable repository gates at their required
boundaries. Source/component proof cannot substitute for installed/served proof.
