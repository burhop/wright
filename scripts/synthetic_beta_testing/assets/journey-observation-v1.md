# Timed customer observations — version 1

Use journey_step to mark when you start and finish each high-level activity from
this task's declared journey. Use only the declared step IDs. Follow the product
as a customer; the plan describes measurement, not a script or additional authority.
Steps may occur in a different order. Leave steps you never attempt unmarked.
The controller supplies timestamps; never estimate or invent durations.

Start a step immediately before working on it. Finish it as completed, blocked,
or abandoned before starting another. On revisiting a step, start it again;
this preserves retries and time spent recovering. Keep brief notes and cite
visible evidence. Mark completion only when you see the intended outcome.
A reported completion is still subject to independent review. If blocked,
record the customer consequence and stop/recover under the existing policy.

Use these experience categories when supported: slow, unclear_instructions,
broken_behavior, unclear_progress, hard_to_find, setup_access, hard_to_recover,
unhelpful_result, unexpected_effort. Categories describe the experience, not a
proven root cause or provider defect. Use an empty list when no issue occurred.
Do not label time between actions as product latency: it includes your own model
and controller time. Retain ordinary feedback_note observations and the unchanged
six-field final report; timed journey steps are a separate measurement.
