## Actual authentication and dynamic loading

`apps/api/src/api/security.py` implements the current authentication boundary using standard-library primitives. `SecuritySettings.token_valid` compares an opaque configured bearer token with `hmac.compare_digest`; `browser_session_token` derives an HMAC-SHA256 session value, separately checked by `browser_session_valid`. The middleware protects HTTP API/MCP requests and sets the authenticated principal role. WebSocket authorization checks the same opaque bearer or browser session. `apps/api/src/api/main.py` exchanges the configured local token for an HttpOnly, SameSite-strict cookie and reports session status. `src/wright_engineering/runtime/auth.py` creates and persists the installation-local token using `secrets.token_hex(32)` and existing containment/permission checks. None of these paths parses, signs, or verifies a JWT.

The independent AST probe parsed all 340 tracked production/adapter Python files under the immutable candidate's `src`, application/package source roots, integrations, and non-test Hermes adapter files. It found no import of `jose`, `ecdsa`, `rsa`, `pyasn1`, or `six`. The four dynamic-loading calls are the fixed repository-local Hermes plugin verifier, NumPy availability detection, and two standard-library datetime imports. I inspected the verifier's target resolution: it loads its own `__init__.py`, not a configured authentication module. Other importlib use is resource/distribution metadata access. No authentication plugin entry point or dynamically selected JOSE provider was found. This is a repository/runtime contract assessment; it cannot promise compatibility for an external consumer relying on an undeclared incidental dependency.
