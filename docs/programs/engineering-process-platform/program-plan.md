## 1. Outcome

Wright will evolve from useful engineering-capability seams and a disposable workflow prototype into a durable engineering-process platform where an engineer can define, inspect, review, run, diagnose, recover, and reproduce multi-step work without confusing fixtures with real analysis or transport success with engineering correctness.

The program is a portfolio of bounded Spec Kit features, not one feature. Each child feature must deliver one independently understandable and reversible outcome, include its own specification/design/tasks/evidence, and pass the same governed lifecycle before integration.

Program success requires all of the following at the same exact release subject:

- **Product readiness:** the user experience, failure behavior, inspectable inputs/outputs, accessibility, security, compatibility, and recovery are proven.
- **Benchmark readiness:** 100 distinct qualified processes meet coverage, oracle, artifact, reproducibility, holdout, and freshness rules.
- **Commercial readiness:** the chosen offering/support posture, packaging, supply chain, privacy, compatibility, operations, repository controls, and exact-subject release train are proven.
- **Program health:** evidence integrity, bounded WIP/repair, risk/decision closure, independent verification, and sustainable delivery remain green.

The four areas are independent release gates. The release function is logical AND, never an average or weighted score.

## 2. Scope and non-goals

In scope:

- a vendor-neutral canonical process definition and engineer-readable projections;
- reviewed human and bounded AI authoring;
- exact provider/model/MCP identities and schema-aware mappings;
- deterministic, live, UI-started, and headless execution through existing Wright authority boundaries;
- durable run/step/activity/evidence/output records with layered failure and recovery;
- actionable artifacts, approvals, feedback loops, compatibility, rollback, and support evidence;
- a 100-process qualification system, governed evidence-derived snapshot, and browser-accessible read-only status page;
- small Spec Kit feature loops governed by machine-readable transitions.

Out of scope until separately approved:

- importing the prototype implementation wholesale or treating any prototype library/schema/UI choice as production architecture;
- representing the full program as one Spec Kit feature;
- generating or filling the 100-process collection during this planning phase;
- paid usage, credentials, license acceptance, proprietary application installation, physical actuation, production/customer data, or external production mutation;
- new dependencies, product code, pushes, PRs, merges, releases, or publications before program approval;
- automatic domain-specific CAD/FEA/CAM/CFD/vendor dispatch in the process runtime;
- promising engineering validity, platform support, SLA, or commercial support without exact supporting evidence.

## 3. Authority and precedence

After digest-bound approval, this directory governs the successor program. Wright's constitution, security boundaries, contributor runbooks, release runbooks, and merge-gate scripts remain higher authority. If they conflict, the stricter rule wins and the conflict is recorded as a decision/risk; it is never silently reconciled.

The earlier engineering capability program remains historical evidence. Feature specs own their bounded outcome and implementation detail; they may refine this plan only through the change-control process. `.specify/feature.json`, task checkboxes, dashboard summaries, and conversation state are not authority.

## 4. Durable design principles

1. **One semantic source, multiple projections.** Text/code, diagram, UI, CLI, headless execution, and evidence views project one versioned canonical definition. View state cannot invent executable state.
2. **Definition and execution are separate.** Immutable run records, not fixtures or canvas objects, own step state, outputs, activity, and findings.
3. **Truth before fluency.** Fixture, validate-only, unconnected, and live modes are explicit everywhere. A user input never receives a predetermined semantic finding.
4. **Layered failure and recovery.** Definition, preflight, semantic needs-input, mapping/schema, approval, execution, outcome evaluation, and cleanup have distinct owners, terminal codes, blocked-dependency behavior, and recovery actions.
5. **Exact authority.** Provider/model/tool/schema/application-surface identities and approval scope are explicit, immutable per run where applicable, and never inferred from a friendly category.
6. **Generic platform boundary.** Engineering domains are discovery and fixture metadata. The runtime does not dispatch by domain, vendor, file format, or benchmark case.
7. **Inspectable work.** Every executable step exposes bounded inputs, human-readable outputs, exact technical evidence, provenance, timing, redaction/truncation, and actionable recovery.
8. **Artifacts are outcomes, not decorations.** Ports, connections, runtime values, artifact references, and reusable components remain distinct. Success must deliver a usable output or an explicit valid no-output result.
9. **Fast contracts plus human evidence.** Pure model/component/contract tests are the default loop. A few cross-boundary journeys and qualified human review catch trust/usability failures tests cannot.
10. **Compatibility is evidence-driven.** Durable schema/interface work declares reader/writer ranges, migration, old-reader behavior, rollback, state retention, and historical-data tests.
11. **Exact subjects.** Approvals, verification, deployment, benchmark qualification, and release evidence bind immutable commits, trees, artifacts, schemas, and environments.
12. **Fail closed.** Missing, skipped, stale, unsupported, partial, ambiguous, or unverifiable evidence is visible and non-passing.

## 5. Program phases

### Phase P0 — Approve and mechanize governance

Approve this exact control plane, resolve the initial authority model, implement the local validator/snapshot generator as `EPP-F01`, and then deliver its browser-accessible read-only projection as the independent `EPP-F01B` child feature. No product feature becomes implementation-eligible until the validator can reject invalid schemas, cycles, stale approvals, missing digests, impossible transitions and conflated readiness areas, and the browser page truthfully renders the same committed evidence without becoming a second authority.

Exit evidence: plan approval record; EPP-F01 validator/snapshot and EPP-F01B browser page independently integrated and deployed on `dev`; the browser page shows four independent areas, `0/100`–`100/100` benchmark progress, active feature/task/checkpoint progress, blockers, next action, evidence and freshness; no active P0 governance defect.

### Phase P1 — Establish the canonical product spine

Deliver the canonical process definition and read-only engineer view, followed by durable run/step evidence and layered failure UX. Preserve vendor neutrality and avoid a permanent renderer/syntax decision unless a separate ADR supports it.

Exit evidence: round-trip/equivalence contracts, representative accessibility/usability evidence, immutable run projection, explicit modes/failures/recovery, compatibility and rollback contracts.

### Phase P2 — Bind and execute through governed boundaries

Deliver exact MCP server/tool/schema selection and schema-aware producer/consumer mapping, then governed execution, authoritative application identity, cancellation/reconnect/deadline behavior, and actionable output delivery.

Exit evidence: generic conformance across structurally different tools; no case/domain dispatch; UI/headless equivalence; safe live subset; artifact/oracle verification; security and authority evidence.

### Phase P3 — Reviewed authoring and composition

Add validated manual/code editing, bounded LLM proposals, semantic diff/accept/reject, and versioned reusable component interfaces only after the canonical and runtime contracts are stable.

Exit evidence: stale-proposal rejection, atomic edits, unchanged execution authority, human usability, compatibility of saved definitions/components, benchmark delta.

### Phase P4 — Qualify breadth and commercial operation

Build the governed benchmark registry/harness, qualify the declared 100-process matrix without leaking holdouts, close commercial/support decisions, rehearse exact-subject packaging/lifecycle/rollback, and stage release.

Exit evidence: all four independent readiness areas pass at one exact candidate; final human release approval; existing Wright release order followed completely.

## 6. Feature readiness envelope

Every product feature specification, plan, checklist, task set, analysis, implementation, and verification must explicitly cover:

- the user and independently shippable user-visible outcome;
- primary, empty, loading, blocked, failure, cancellation, reconnect, stale, and recovery states;
- inspectable input identity/provenance and output/artifact identity/lifetime/actions;
- deterministic unit/component/contract tests and proportional integration/human evidence;
- accessibility, narrow/zoomed/reduced-motion behavior when UI is touched;
- security, privacy/egress, approvals, redaction, cleanup, and authority boundaries;
- compatibility range, migration, previous-stable behavior, rollback, offline/restart/uninstall implications;
- benchmark coverage delta, affected holdout policy, new oracle/failure-injection needs, and anti-case-branch review;
- documentation, support diagnostics, telemetry posture, packaging, and release impact;
- exact stop conditions and rollback identity.

Absence of any item blocks implementation approval. `speckit-checklist` tests the quality of these written requirements; it is not executable product verification.

## 7. Evidence model

Every lifecycle transition is an append-only record conforming to [`schemas/transition-evidence.schema.json`](schemas/transition-evidence.schema.json). It binds prior/current state revisions and digests, actor role, action, inputs/outputs and digests, Git subjects, environment, checks including original failures, approval, independent verifier, repair count/cause, blockers, rollback, and next action.

The state snapshot is compare-and-swap: its prior revision/digest must match the accepted transition. No transition may be inferred from files merely existing, task boxes being checked, tests passing on another tree, or a dashboard being green.

Historical evidence is never rewritten to repair factual metadata. The exact closed `COR-EPP-F01-US1-COMMITTED-IDENTITY-001` profile may dispose only its six transition-digest and 31 state-tree pointer claims after V4 approval and `37/37` Git recomputation. The separate `COR-EPP-F01-US1-TR0027-INPUT-ORIGIN-001` profile may dispose only TR-0027 `/inputs/3` after V5 approval and `1/1` source-absence/unique-container proof. The proposed `COR-EPP-F01-REPAIR-EVIDENCE-001` profile may dispose only its two ordered claims—two exact invalid cause-ID occurrences and one exact truncated TR-0043 digest pointer—after V7 approval, `2/2` claim/occurrence proof, and exact Git rehashing. None is a general exception. Original bytes/findings remain visible; partial, extra, generic, current, future, circular, manifest, lifecycle, authority, readiness, benchmark, gate, candidate, delivery, freshness, and release targets fail closed. A correction cannot correct another correction. Unsupported readers fail closed.

## 8. Human approvals and autonomy

Human approval is required for:

- this program plan and any material scope/gate/authority change;
- each child feature's exact spec/plan/checklist/tasks/analysis before implementation;
- any P0 decision or exception, dependency addition, public/durable compatibility break, data migration with loss risk, security/privacy/telemetry policy change, proprietary/paid/credentialed/hardware activity, or external production mutation;
- push/PR authority unless explicitly granted in the feature charter; every merge to `dev`; every `dev` to `main` integration; and every publication/release.

Within an approved feature charter, the owning agent may perform isolated local edits, focused tests, local commits with allowlisted staging, and bounded repairs. Authorization never expands because work is difficult or nearly complete.

## 9. Change control

Material changes include user scope, readiness criteria, dependencies, architecture boundaries, persisted/public schemas, security/privacy, benchmark sampling/oracles/holdouts, compatibility/support claims, release order, approval roles, WIP/repair limits, or roadmap dependencies.

Any historical correction or change to its profile, target set, origin/identity proof, resolution semantics, compatibility behavior, or readiness/authority non-interference proof is material. It invalidates current feature authority and requires a new exact digest-bound decision; it is never treated as editorial repair.

A material change requires:

1. a decision record and affected risk/gate/roadmap updates;
2. invalidation of downstream approvals/evidence whose subjects changed;
3. return to the earliest affected lifecycle state;
4. rerun of all downstream Spec Kit artifacts and independent analysis;
5. a new digest-bound human approval.

Editorial changes may proceed only when they do not change semantics; the transition still records changed digests and rationale.

## 10. Program completion

The program is complete only when:

- the agreed product outcome is shipped and independently verified;
- all 100 counted processes are current at their declared qualification levels and their coverage/oracle rules pass;
- commercial readiness matches an explicit approved posture and exact support claims;
- program health has no open release-blocking P0 risk/question/exception;
- the exact candidate satisfies dev integration, production merge, build-once promotion, public package/container/native lifecycle, documentation, and GitHub Release-last rules;
- rollback and compatibility evidence exists for the same subjects;
- final human approval is recorded.

Merging a PR, passing 100 processes, completing a rehearsal, or pushing `main` is not program completion by itself.
